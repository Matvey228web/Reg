# Как выкладывается система

| Что | Куда | Чем |
|---|---|---|
| Склад (`app/`) | Pages, проект `mifs-rent` | `wrangler pages deploy` |
| Сайт проката (`site/`) | Pages, проект `mifs-site` | `wrangler pages deploy` |
| Бэкенд (`apps-script/Code.gs`) | Apps Script в таблице | `node apps-script/deploy.js push` |
| Worker (`worker/`) | Cloudflare Workers, `mifs-rent-api` | `npx wrangler deploy` |

Компьютер не нужен ни для одной из частей.

### Порядок выкладки

1. **Бэкенд:** `node apps-script/deploy.js push`.
2. **Worker:** `cd worker && npx wrangler deploy`.
3. **Склад и сайт** — Pages, как описано ниже в «Приложение и сайт».

Порядок от таблицы к экрану: новая кнопка или поле в приложении опирается на
ручку и настройку в `Code.gs`, и выложенное раньше бэкенда приложение первые
минуты получало бы отказы.

Склад и сайт — **разные проекты Pages** намеренно: у каждого свой адрес, свои
правила кэша и своя выкладка, и сайт можно перевезти на другой хостинг, не
трогая склад.

### Выкладывают только руками, ничего — автосборкой

Ни Worker, ни проекты Pages не подключаются к GitHub (Cloudflare → Settings
→ Build → Git repository должно быть пусто). 1 октября 2026 к Worker
`mifs-rent-api` была подключена автосборка: на каждый пуш она собирала
репозиторий без `worker/wrangler.toml` и выкладывала статику склада поверх
API. Приложение писало «Нет связи с сервером» на всех экранах, а заодно
пропадал секрет `TELEGRAM_BOT_TOKEN`.

После любой выкладки и после любого пуша — одна проверка:

```sh
curl -s https://mifs-rent-api.odintsovmatvey08.workers.dev/
# должно быть: Mifs Rent API. Запросы принимаются через POST.
```

Если вместо этого пришла HTML-страница — Worker затёрт: выложить заново
(`cd worker && npx wrangler deploy`), проверить `npx wrangler secret list`
и найти, что его затёрло.

## Бэкенд

`apps-script/deploy.js` делает мышиную последовательность запросами:

1. забирает содержимое проекта и **сверяет с репозиторием**;
2. кладёт новый `Code.gs`, не трогая остальные файлы;
3. создаёт версию;
4. переводит на неё **существующее** развёртывание.

Четвёртый шаг важен: адрес `/exec` и есть идентификатор развёртывания. «New
deployment» выдал бы новый адрес, и приложение продолжило бы стучаться в старую
версию.

### Команды

```sh
node apps-script/deploy.js show          # что сейчас в проекте, ничего не меняет
node apps-script/deploy.js push          # сверить и выложить
node apps-script/deploy.js push --yes    # выложить, приняв различия
node apps-script/deploy.js verify        # спросить живой бэкенд про эндпоинты
```

### Почему `push` может отказаться

Если живой код отличается от репозитория, `push` показывает различия двумя
столбцами — «исчезнет из таблицы» и «появится в таблице» — и останавливается
с кодом 2.

Так уже было: в редакторе руками переименовали категорию, в репозитории осталось
старое название. Выкладка без просмотра затёрла бы правку молча.

Увидели в столбце «исчезнет» что-то, чего не писали сами, — сначала перенесите
это в репозиторий, потом выкладывайте с `--yes`. Копия того, что лежало в
таблице до выкладки, остаётся во временной папке, путь печатается.

Script API**.

Один раз на сессию Claude Code (контейнер временный, токен исчезает с ним):

3. Браузер покажет ошибку на `localhost:8888` — так и должно быть. Скопировать

### Права

| Право | Зачем |
|---|---|
| `script.projects` | читать и записывать содержимое проекта |
| `script.deployments` | создавать версии и переводить развёртывание |
| `script.webapp.deploy` | публикация веб-приложения |
| `drive.metadata.readonly` | найти проект, если потерялся Script ID |

Ни таблиц, ни почты, ни `cloud-platform`. Используется OAuth-клиент утилиты
`clasp` — он опубликован Google, поэтому refresh-токен живёт до отзыва (свой
клиент в статусе «Testing» выдавал бы токен на 7 дней).

Отозвать: `myaccount.google.com` → Безопасность → Сторонние приложения → clasp.

### Чего конвейер не делает

- **Не ускоряет бэкенд.** Apps Script отвечает 6–9 секунд на чтение. От этого
  спасает Worker перед таблицей (`worker/`) — включён, и через него ходят и
  сайт, и склад. Первое чтение всё равно упирается в таблицу; дальше кэш.
- **Не спасает от HTML вместо ответа.** Запрос к `/exec` уходит редиректом на
  `script.googleusercontent.com`; когда второй запрос не доходит, в приложение
  приезжает страница Google вместо JSON — это и есть «Некорректный ответ
  сервера». Лечится тем же Worker.
- **Не запускает `setupSheets`.** Добавились вкладки или колонки — функцию надо
  один раз запустить из редактора.
- **Не ставит триггеры.** Ночное обслуживание заводит `setupTriggers` — тоже
  один раз из редактора (см. ниже).

### Разовые шаги после выкладки ночного обслуживания и журнала

Делаются руками один раз, в редакторе Apps Script (таблица → **Расширения** →
**Apps Script**), функция выбирается в списке наверху, кнопка **Run**:

1. **`setupSheets`** — в таблице появится лист `Logs` (журнал сбоев).
   Повторный запуск безопасен: существующие листы он не трогает.
2. **`setupTriggers`** — ставит ежедневный `dailyMaintenance` около 3:00 и
   снимает прежние, включая убранный `dailyOverdueDigest`. Google спросит
   **новое разрешение** — на запуск по расписанию, когда вас нет рядом;
   разрешите. Повторный запуск тоже безопасен.
3. Слева часы (**Triggers**): в списке должен быть **ровно один** триггер —
   `dailyMaintenance`. Два, или остался `dailyOverdueDigest` — запустите
   `setupTriggers` ещё раз.
4. В приложении: Настройки → «Адреса и связи» → **«Тема для заявок»** и
   **«Тема для актов»** — номера тем форума (как их узнать — `BOT.md`,
   шаг 4б).

Что делает `dailyMaintenance` каждую ночь: копирует таблицу целиком в папку
Диска **«Mifs Rent — копии»** под именем «Mifs Rent ГГГГ-ММ-ДД», держит там
14 последних копий (старые уходят в корзину Диска, откуда их ещё 30 дней можно
достать) и убирает из `Logs` строки старше 90 дней. В чат не пишет; неудачу —
строкой в `Logs`.

Подробности — по ссылкам; здесь только порядок.

   Расширения → Apps Script), **Run** → в таблице появился лист `Logs`.
2. **[раз]** Запустить `setupTriggers` → там же, разрешить новый запрос
   доступа Google → в разделе **Triggers** ровно один `dailyMaintenance`

   на `/id`.
4. **[раз]** `/id` внутри каждой темы → номера вписать в приложении:

12. Пробная заявка с сайта → через несколько минут сообщение в теме «ЗАЯВКИ»

## Приложение и сайт

```sh
npx wrangler@latest pages deploy <папка> --project-name=mifs-rent \
  --branch=main --commit-dirty=true
```

Папка склада собирается из `app/`: `index.html`, `_headers`, `css/`, `js/`.
Папка сайта — `site/` плюс свой `_headers`. Привязки к Git у проектов нет
намеренно.

**Из копии склада перед `wrangler pages deploy` удаляется `js/mock-data.js`.**
В нём живые персональные данные (ФИО, телефоны, заказы), а всё, что лежит в
папке выкладки, открывается по прямой ссылке любому — неважно, что
`index.html` подключает файл только при `MOCK_MODE`. Демо-режим — для запуска
на своей машине, в опубликованном приложении он не нужен.

```sh
rm -rf /tmp/mifs-app && mkdir /tmp/mifs-app
cp -r app/index.html app/_headers app/css app/js /tmp/mifs-app/
rm /tmp/mifs-app/js/mock-data.js
npx wrangler@latest pages deploy /tmp/mifs-app --project-name=mifs-rent \
  --branch=main --commit-dirty=true
```

После выкладки проверить: `<адрес приложения>/js/mock-data.js` должен отдавать
404. Оговорка: без `404.html` в папке Pages считает проект одностраничным и на
несуществующий путь может ответить кодом 200 со страницей `index.html` — это
тоже значит «файла нет». Плохо, только если в ответе JavaScript с `MockStore`:
файл попал в выкладку, собрать папку заново по шагам выше.

Перед выкладкой сайта пересобирается снимок каталога:

```sh
node site/build-catalog.js
```

Он делает один запрос к `/public/catalog` и пишет `site/catalog.json`. Витрина
читает этот файл и открывается мгновенно; наличие на даты сайт спрашивает у
бэкенда сам, когда даты выбраны.

**Новый проект Pages** создаётся не через `wrangler pages project create` —
в версиях от 4.14 эта команда уводит в Workers. Через API:

```sh
curl -X POST "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/pages/projects" \
  -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"имя","production_branch":"main"}'
```

`?v=<версия>` в ссылках на свои файлы поднимаем каждой выкладкой. Работает это
только вместе с `_headers`, который запрещает кэшировать саму страницу: WebView
Telegram держит её жадно, и иначе внутри старой страницы остаются старые ссылки.

Токен Cloudflare нужен с правами Pages → Edit и тоже живёт только в песочнице
сессии.

## Где смотреть, когда что-то сломалось

- **Лист `Logs` в таблице.** Сюда пишется всё служебное: ошибки сервера,
  отказы Telegram, откат сообщения из темы в General, несобравшийся акт,
  неудачная ночная копия. В чат склада это не идёт. Колонки: время, что
  (`kind`), где (`endpoint`), причина, текст, подробности.
- **`GET https://mifs-rent-api.odintsovmatvey08.workers.dev/health`** —
  состояние очереди заявок в Worker: `queue` — сколько заявок ещё не доехало
  до таблицы (норма — 0, иногда 1–2 на пять минут до следующего захода cron),
  `dead` — сколько отложено как недоставляемые, `oldest_dead_at` — когда
  появилась самая старая. Опрашивать внешним мониторингом **не чаще раза в
  15 минут**: каждый вызов тратит операции KV, а их на бесплатном тарифе около
  тысячи в сутки на всё.
- **Ключи `dead:` в Cloudflare KV** — сами недоставленные заявки: Cloudflare →
  **Storage & Databases** → **KV** → `mifs-rent-cache` → поиск по `dead:`. В
  значении — текст заявки (`payload.raw_text`) и причина (`error`).
- **Папка Диска «Mifs Rent — копии»** — 14 ночных копий таблицы. Если данные в
  таблице испорчены, отсюда их можно достать.

Опрашивать `/health` снаружи — см. «Внешняя проверка: UptimeRobot» ниже.

## Внешняя проверка: UptimeRobot

Лист `Logs` и `/health` сами ни о чём не сообщают — в них надо заглянуть.
Внешняя проверка заглядывает за вас и пишет на почту, когда Worker перестал
отвечать. Всё делается с iPhone, в браузере.

1. Зайти на `uptimerobot.com`, завести **бесплатную** учётную запись на почту
   владельца и подтвердить её письмом.
2. Добавить новый монитор (кнопка добавления на главной панели).
3. Тип — **Keyword**, если бесплатный тариф его даёт: адрес
   `https://mifs-rent-api.odintsovmatvey08.workers.dev/health`, искомое слово
   `"ok":true`, тревога — когда слова **нет**. Если Keyword недоступен — тип
   **HTTP(s)** с тем же адресом: он заметит только полное молчание или код
   ошибки, но и это лучше, чем ничего.
4. Интервал — **15 минут, не меньше.** Каждый вызов `/health` тратит две
   операции `list` в KV, на бесплатном тарифе их около тысячи в сутки на всё,
   и 288 из них уже съедает cron. Раз в 15 минут — ещё 192 в сутки; раз в
   5 минут — 576, и вместе с cron это впритык к пределу.
5. Контакт для тревог — почта владельца (её UptimeRobot предложит сам).
   Сохранить.
6. Через 15–30 минут монитор должен стоять зелёным («Up»).

**Пришло письмо «Down».** Значит, `/health` не ответил или ответил без
`"ok":true`. Первые три проверки:

1. **Worker затёрт.** Открыть `…workers.dev/` в браузере: вместо «Mifs Rent
   API…» HTML-страница — см. «Выкладывают только руками» в начале файла.
2. **`dead` больше нуля** в ответе `/health` — есть недоставленные заявки, см.
   «Заявки не доходят» ниже.
3. **Таблица не отвечает.** `queue` растёт, а в приложении «Нет связи с
   сервером» — Apps Script лежит или его развёртывание сбито: последние строки
   `Logs`, затем `node apps-script/deploy.js verify` (или откат, см. «Откат»).

Короткое «Down» на 15 минут и тут же «Up» — обычно сбой у Cloudflare или
Google, а не у нас; разбираться, только если повторяется.

## Откат

Откатывается каждая часть отдельно; начинайте с той, что выкладывали
последней.

- **Apps Script.** Редактор → **Deploy** → **Manage deployments** → карандаш у
  рабочего развёртывания → в поле **Version** выберите предыдущую → **Deploy**.
  Именно правка существующего, не **New deployment**: новое развёртывание — это
  новый адрес `/exec`, и Worker продолжит стучаться в старый.
- **Worker.** `cd worker && npx wrangler rollback` — вернёт предыдущую версию.
  Или в панели: Workers & Pages → `mifs-rent-api` → **Deployments** → у
  нужной версии **Rollback**.
- **Pages** (склад, сайт). Workers & Pages → проект (`mifs-rent` или
  `mifs-site`) → **Deployments** → у прежней выкладки три точки →
  **Rollback to this deployment**.

Откат Apps Script не убирает лист `Logs` и триггер: старый код их просто не
использует, а `dailyMaintenance` без своей функции будет падать с ошибкой в
списке запусков — это безвредно, до следующей выкладки.

## Запасной человек: завхоз

Если разработчика нет, систему поддерживает завхоз. Ему нужно:

- **редактор таблицы** склада и, через неё, **проекта Apps Script**;
- **участник аккаунта Cloudflare** с доступом к Workers (и Pages, если
  выкладывать приложение);
- **токен бота** — только если придётся заново задавать секрет Worker
  (`BOT.md`, шаг 3б). Токен хранится в менеджере паролей и **никогда** не
  пересылается в чат.

### Выложить заново

1. Взять свежий репозиторий: `git pull` (или скачать архив ветки `main`).
2. Бэкенд: `node apps-script/deploy.js push`. Без токена конвейера — руками:
   вставить `apps-script/Code.gs` в редактор, сохранить, **Deploy** →
   **Manage deployments** → карандаш → **Version: New version** → **Deploy**.
3. Проверить бэкенд: `node apps-script/deploy.js verify` — `/labels/send`
   должен ответить `410`, это знак, что выложен свежий `Code.gs`.
4. Worker: `cd worker && npx wrangler deploy` (первый раз —
   `npx wrangler login`).
5. Открыть `…workers.dev/health` в браузере: должно быть `"ok": true`.
6. Склад и сайт — командами из «Приложение и сайт» выше.
7. Открыть склад из Telegram, посмотреть каталог и нажать «Поздороваться в
   чате» — бот должен ответить в группе.

### Заявки не доходят

1. Открыть `…workers.dev/health`. `queue` больше нуля и растёт — Worker не может
   достучаться до таблицы; `dead` больше нуля — есть отложенные заявки.
2. Посмотреть последние строки листа `Logs`: ошибки сервера и отказы Telegram
   там с причиной.
3. Заявка есть в «Заказах», но не в чате — дело в боте: причина в `Logs`
   (`kind` = `telegram`). Чаще всего бота удалили из группы, сняли с него
   администратора или поменялся номер темы.
4. Заявки нет и в «Заказах» — проверить Настройки → «Заявки с сайта»: приём
   включён? Выключенный приём складывает заявки в `dead:`.
5. Разобрать `dead:` в Cloudflare KV: прочитать `error`, текст заявки
   (`payload.raw_text`) вставить на экране «Заказы» как сообщение бота, затем
   ключ удалить.
6. Сделать пробную заявку с сайта и через пять минут снова открыть `/health`:
   `queue` и `dead` должны быть нулями.
